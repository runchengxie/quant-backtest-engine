# 合成数据 CLI 批处理基准

[English](benchmarks.md)

本实验表明，调用方可以并发启动独立进程，运行这些很小的合成请求。
计时包含进程启动、读取样例、引擎计算和 JSON 输出，不能据此判断生产容量、
编译速度或其他实现的性能。

先准备已经核实来源的引擎程序，再在源码目录运行下面的命令。

```bash
python project_tools/benchmark.py \
  --engine /absolute/path/to/quant-backtest-engine \
  --engine-revision FULL_SOURCE_COMMIT --build-profile debug \
  --output /absolute/external/path/benchmark.json \
  --jobs 24 --concurrency 1,2,4 --timeout 30
```

输出路径必须位于检出目录之外，且文件不能已存在。每个样例先单独预热，
再按各并发数分别运行一批独立进程。能力查询也单独计时。
报告记录二进制大小及 SHA-256、样例哈希、环境、每次耗时、整批吞吐量，
以及按最近秩法计算的 p50/p95 延迟。延迟从工作线程开始启动进程时算起，
不包含等待线程空闲的时间。吞吐量只统计成功任务。

同一样例的所有结果均须与预热结果的规范化 JSON 摘要一致。非零退出、
超时、无效 JSON 和摘要不一致都会明确记为错误。报告写出后，脚本以非零状态退出。
超时会终止整个进程组。错误信息可能含本地路径，分享报告前应检查。
Linux 上若有 GNU `/usr/bin/time`，报告会记录单个子进程的最大常驻内存，单位 KiB。
子进程峰值之和不能代表并发批次的内存峰值。缺少测量工具时会明确记录。

## 2026-10-31 实测

二进制对应源码 `3ee74bfa21d743e595ce61d0ac06b97dd588ebd6`，debug 构建，
38,252,752 字节，SHA-256，
`9ed68e44f6eb9f8861b3c57ede6300e23db5d6fd5d8f80f7afbb2ecdae6c18c7`。
环境为 Linux x86-64、Intel Core i5-4690K 3.50 GHz、四个逻辑 CPU、Python 3.14.8。
系统没有 GNU `/usr/bin/time`，因此没有 RSS 测量值。
两个版本化样例均测试了每批 12/24 个任务、并发数 1/2/4。全部成功，结果摘要均与预热一致。

表中延迟列为 p50/p95，单位毫秒。吞吐量为每秒成功任务数。
这些不足一秒的批次能说明本机可以重叠执行独立 CLI 任务，但容易受到启动开销、
调度和其他负载影响。12 和 24 个任务的运行各提供一个独立样本。要估计置信区间，还需重复测量。
能力查询只能粗略参考进程启动和序列化开销，不能相减得到纯计算时间。
部署前需要更有代表性的大规模合成数据、重复运行和 release 构建测量。
本实验没有测量 release 构建，也没有其他语言的基线。
任务调度和资源限制由调用方负责，脚本没有给引擎增加任务服务。

## 较大规模的确定性工作负载

开发示例 `profile_sessions` 在现有逐交易日执行路径中加入可选计时，不改变请求和
结果协议。运行方法见[源码 README](https://github.com/runchengxie/quant-backtest-engine#readme)
中的 `project_tools/profile_workload.py`。默认输入为 63 个合成工作日、100 个证券、
每日 241 个分钟时间点，共 1,518,300 行报价。每个证券每天提交一笔订单，买卖按日
交替。这覆盖多证券加载、撮合、上游核算和每日账本提取，不代表真实行情、公司行为、
日内组合决策或大量竞争订单的表现。

运行器保留版本化合成输入及哈希，至少运行三次独立子进程，分别记录数量规划、
实际订单与成交数量、结果哈希，并核对现金加持仓市值等于净值、每日手续费合计及
持仓市值合计。小规模预热需另行运行；预热、debug 与 release 数据不能混用。

计时分别覆盖验证与克隆、初始化（含全部报价规则及订单准备）、报价转换和加载、
回放、每日快照和数据清理、最终收尾。撮合与核算共用上游回放阶段，不能拆成独立
数字。内存每 10 毫秒读取子进程 RSS，采样最大值是实际峰值的下界，不含 Python
生成输入的内存，也不代表分阶段内存分配量。运行器默认在采样 RSS 超过 6144 MiB 时停止子进程并记录；这不是操作系统内存
上限，采样可能漏过短暂峰值，也不限制父进程生成输入的内存。
输入读取与解码、结果编码单独计时；诊断包装编码、输出传输和轮询开销仍计入完整
耗时。这些数据只描述指定机器和工作负载，不能直接推算生产容量。

## 广泛证券池与稀疏执行

`project_tools/sparse_workload.py` 区分登记证券池和预先固定的订单。每个会话仅对
`--active` 个合成证券下单，同一组在下一会话卖出，再轮换下一组。这是每日二十笔
订单的测试，不表示每日轮换二十只持仓只需二十笔订单。独立数量规划探针也不包含
全市场选股、风险估计和组合优化。

`all` 保留全部分钟报价。`orders-and-valuation` 保留活动证券的分钟报价，并在每个
会话估值边界为所有登记证券保留新鲜报价。它仅适用于本例的固定订单执行消费者，
不能用于删减盘中信号、风险或跨资产冲击消费者所需的数据。历史缺失或停牌证券的
估值证据不能用合成价格补齐。解读路由基准前，应先验证小规模完整与路由输入的
财务结果完全一致。

默认二百万行报价预算在分配完整输入前检查，超出时只保存计划并明确返回未执行，
不会偷偷缩减证券数或日期。子进程 RSS 仍为采样下界，不含输入生成器，行数预算也
不是操作系统内存保证。六千证券仅为合成规模例子，不是当前上市证券数。所有变体
均为一分钟间隔，减少时间点会缩短会话，不代表对同区间降低采样频率。

## 待执行订单索引，2026-11-04

会话回放按会话和证券组织待执行订单。每条报价只检查对应分组，保留请求中的订单
顺序，并严格要求 `information_ts_ns < quote.ts_ns`。符合条件的订单通过一次遍历
取出，不再逐笔移动整个季度剩余的订单。账户读取、含手续费的现金准入、T+1
可卖数量预留、报价交易权限和上游 IOC 撮合仍走原有执行路径。
`strategy_pending_checks` 统计逐笔订单的资格检查次数，包含首次探测和随后准入
遍历中的检查，不包含索引查询次数。

对照版本为 `c33434d4a5f96eb947d71a751ef25bd434dd3d5e`，使用 Linux x86-64、
Rust 1.99.1 和 release 构建。每个二进制针对每组确定性输入分别预热一次，再启动
三个独立子进程测量。输入由现有工具的
`generate_sparse(8, 120, 6, 30, "all", 100000)` 和 `generate(8, 20, 20)` 生成，
通过不属于公开协议的 `profile_sessions` 示例执行。

| 输入 | 报价数 / 订单数 | 优化前 / 后待执行订单检查次数 | 优化前 / 后完整耗时范围（秒） |
| --- | --- | --- | --- |
| 八会话稀疏交易 | 28,800 / 48 | 605,448 / 96 | 0.256–0.365 / 0.257–0.416 |
| 八会话密集交易 | 3,200 / 160 | 225,840 / 320 | 0.087–0.097 / 0.084–0.092 |

所有运行的完整财务结果对象在优化前后均一致。规范化结果的 SHA-256 为
`c9f864adab63e77f0e5ed909738eb3d201f3705c64774cbc12789e0840a09c7d`（稀疏）和
`56a6d73ef65d7959c43d1b4d06928924faa16f680d010eeae1ab00a9933beec2`（密集）。
两组订单全部成交且无拒单，账户读取次数分别仍为 48 和 160。另一个操作次数回归
将 103 笔订单保留在两个会话、两个证券中：八条报价只检查对应分组中的订单 206
次，优化前全局遍历为 824 次。

这些小规模运行证明订单检查次数下降且财务结果一致，不能证明端到端加速或全市场
容量。完整耗时范围重叠，包含输入解码、初始化、回放和输出。同一分组中尚未满足
信息时间条件的订单仍会被遍历；报价规则存储、整份请求克隆、报价加载、上游记账
和内存限制均未改变。本次变更不包含季度规模实测或流式输入重构。
