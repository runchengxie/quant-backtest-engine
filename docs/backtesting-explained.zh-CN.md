# 回测为什么不能只看一条净值线

[English](backtesting-explained.md)

预测要变成收益，先得有钱下单，订单还得成交。成交后的现金和持仓，又会影响下一次决策。净值曲线把这些过程压成了一个数字。下面从一笔订单开始，顺着实际股数和现金看下去，再逐项改变执行条件。

这里的例子来自各场景旁链接的公开实现，输入全部是合成数据。较完整的执行、冲击和优化功能属于 Python Platform，Rust Engine 的能力范围另有明确契约。真实盘口校准、历史集合竞价排队和未来业绩仍没有得到这些例子的验证。

关闭 JavaScript 也能读到全部数值表。点击**播放**后画面才会推进，也可以用**下一步**逐个事件查看。情境选项对应事先由原实现算好的结果，浏览器不撮合订单，不重算金融模型。表格保留实现输出的金额精度，较长的小数并不代表经济测量更准确。

## 1. 从预测走到账户

**每次决策都要接着实际成交后的账户往下做。**

策略给出预测，规划器把目标转成可行订单。执行模块决定哪些订单能成交，并结算费用。下一次决策看到的现金、持仓和未结订单，都来自这一步。Runtime 负责进程管理与恢复，撮合和记账仍由原来的实现负责。

先看 Rust Engine 已有的往返交易例子。账户买入10股，每股10美元，随后按12美元卖出这10股。11美元的报价来得更晚，没有成为卖出价。两次交易各收10个基点的费用，合计0.22美元，期末现金为10,019.78美元。订单只能使用信息时点之后严格更晚的合格报价。这个例子检查给定订单的成交与账本是否一致，其中没有预测优化器。

<!-- method:flow -->

??? details "账怎么算，下一步怎么做"
    `10,000 − 10 × 10 − 0.10 + 10 × 12 − 0.12 = 10,019.78`。
    表内信息时点与成交时点都以 UTC 纳秒表示，保存为字符串，避免浏览器把大整数四舍五入。

    滚动规划通常只执行当前计划的第一个动作，再根据新状态重新规划。[Boyd 等人的论文](https://stanford.edu/~boyd/papers/cvx_portfolio.html)介绍了这种多期交易方法，不能据此判断这里的合成预测有多准。可以接着运行 [Engine 目标权重教程](tutorial.zh-CN.md)。

## 2. 订单碰到有限的盘口

**屏幕上的价格，只能对应当时可用的成交数量。**

合成盘口的买一价为99。卖盘在101价位只有5股，110价位还有10股。一笔限价110、买入20股的订单，先拿到较近的5股，再拿到下一档10股，仍有5股未成交。成交金额是 `5 × 101 + 10 × 110 = 1,605`，成交均价为107。

表里的两行成交发生在同一个1,000毫秒撮合事件中，分开展示是为了看清挂单如何减少。最后一行把报告送达设在1,600毫秒。这个600毫秒延迟是明确设定的画面示意。后面的恢复场景会使用财务会话自身的延迟报告机制。

<!-- method:book -->

??? details "价差、深度与证据范围"
    初始买卖价差为 `101 − 99 = 2`。价格单位是每股合成货币单位，时钟为经过的毫秒数。成交由 Python Platform 的 ticknet 价格时间优先撮合器生成。这个示意没有重建历史排队，也没有推断隐藏流动性或实现集合竞价优先级。部分成交后仍有未完成数量，期末估值不会替它补上一笔成交。

## 3. 成交之后还会留下什么

**外部价格和自己交易造成的假设冲击，需要分开看。**

先把未受自身交易影响的价格固定在10。基准情境中，买入100股会让暂时偏移增加0.2。成交价的平均偏移为0.1，因为实现把本笔订单新增偏移的一半计入成交价。经过60秒，剩余暂时偏移约为0.0735758882。下一笔买单到来时，会遇到这个尚未消退的状态。

可以分别比较更大的订单、更近的间隔，以及明确不衰减的压力假设。页面只提供已经算好的离散选项，这些参数没有经过市场校准。基准中的不衰减项为零，非零情境用来检查结果对该假设有多敏感。

<!-- method:impact -->

??? details "公式与单位"
    对带方向的成交股数 `q`，执行前的暂时状态为 `x⁻ = x × exp(−Δt / τ)`。成交偏移为 `x⁻ + p + (η + γ)q/2`，执行后的状态为 `x⁺ = x⁻ + ηq`、`p⁺ = p + γq`。这里 `η = 0.002`，单位是每股带来的价格偏移，`τ = 60` 秒。`γ` 取零或选项中明确给出的不衰减压力系数。

    曲线画出各项状态偏移，外部价格对应零偏移基线。表格另行保留外部价格，以及当时的成交或标记偏移。同一秒的衰减和成交分成两行显示。[Obizhaeva 与 Wang 的研究](https://web.mit.edu/wangj/www/pap/ObizhaevaWang13.pdf)讨论了动态流动性和恢复过程，没有为这里的系数提供校准，也没有证明某个市场一定存在永久冲击。

## 4. 一笔成本扣一次

**已经包含在成交价里的成本，不要再当手续费扣一遍。**

100股按10.1成交，手续费前的金额是1,010。相对未受影响的价格10，成交价里已经包含10元冲击成本。再加1元最低佣金，现金总共减少1,011。初始现金12,000，交易后剩10,989。冲击模型只更新一次，账本也只扣一次。

价差和价格冲击影响成交价，佣金另行从现金扣除。基准短缺还会描述等待或未成交造成的差额，这些比较值不会自动变成新的现金支出。如果再扣一次那10元冲击成本，就会错误地得到10,979。

<!-- method:cost -->

??? details "现金支出与机会损失"
    这笔买入遵守 `交易后现金 = 交易前现金 − 成交金额 − 现金费用`。这里使用每股0.002的不衰减敏感性假设，与上一节的暂时冲击基准不同。

    简单的买入基准分解，可以分别比较已成交数量乘以成交价差、明确费用，以及未成交数量乘以指定比较价差。最后一项依赖基准选取，只用于描述机会损失，不进入现金扣款。[成交与估值假设](execution.zh-CN.md)说明了 Engine 自身支持的价格和费用语义。

## 5. 整股和最低费用会改变可行解

**舍入和固定成本，会改变哪些组合买得起。**

两项资产的价格分别是6和4，现金为14，每项可以买零到三股。当目标都是1.6股、没有最低费时，最好的可行组合是 `(1, 2)`。每笔非零订单加上1元最低费后，答案变成 `(1, 1)`，剩余现金为2。

第三个选项把目标改成 `(1.5, 1.5)`，列出全部16个网格点。最低费存在时，只有7个点可行。`(1, 1)` 的平方跟踪误差最小，为0.5。这里的启发式结果恰好与有限域最优解相同，这只是该例子的结果。

<!-- method:lots -->

??? details "目标函数与资金约束"
    在 `{0,1,2,3}²` 的整数持仓中，满足现金和费用约束后，最小化 `(qA − targetA)² + (qB − targetB)²`。买入和全部费用必须事先备足资金。卖出预期所得要等原账本实际结算，才能用于后续买入。穷举最优的结论仅适用于这个明确的小范围，不外推到一般非凸问题。

## 6. 分开改变执行条件和市场路径

**预测可以相同，账户和下一次决策仍要各自重跑。**

前两个情境的预测输入和外部价格完全相同，只有参与率上限不同。容量较小的账户买到200股，容量较大的账户买到1,000股，各自的现金和未结订单独立变化。把最后一个外部价格改成10.5，较小账户的后续成本又会改变。这次变的是市场路径，与成交容量的变化分开记录。

反馈情境在下一次决策时读到实际买入的100股，把目标权重改为0.1，保留这部分持仓。它没有继续追逐原先的满仓请求。决策行保留了当时真实可见的现金和未结订单状态。同一份预测反复回放，也不会增加真实市场的独立观察次数。

<!-- method:paths -->

??? details "哪些步骤确实重算了"
    每个情境都用全新账户调用公开分钟执行实现。决策读取严格更早的价格标记，以及当时可见的持仓。这里明确给出一个简单规则，存在未结订单时保留它；反馈选项则改为实际持仓对应的权重。导出文件分别保存预测和市场数据的哈希，还保留完整订单与成交。页面没有训练预测模型，浏览器也不运行模拟器。

## 7. 没赢的尝试也要留下

**从历史结果里挑最大值，会改变这个结果能说明什么。**

公开无信号例子有四个合成收益，两项为 `−1/64`，两项为 `+1/64`，给定预测与收益的协方差为零。教学搜索事先声明全部六种两资产等权组合，再用同一组四个观察值评分，选出最大值。

六个分数依次是 `−1/64、0、0、0、0、+1/64`。胜出的1.5625%能看见，亏损和零收益的尝试也都留下来。六个分数的平均值为零。这个有限例子展示了在无信号构造中挑最大值也会得到好看的数字，没有估计真实策略误报的概率。

<!-- method:selection -->

??? details "搜索证据到哪里为止"
    这里是在公开无信号样例上执行的固定脚本穷举，范围仅限教学。它没有导入私人研究，没有运行自适应研究任务，也没有显著性检验或新的样本外结果。[Bailey 等人的论文](https://www.davidhbailey.com/dhbpapers/backtest-prob.pdf)讨论了反复选择配置带来的回测过拟合，其 PBO/CSCV 方法与这个简单演示不同。讨论选择结果前，先保留全部尝试。

## 8. 恢复成功，退出也可能没有完成

**交易限制和未结状态要继续保留，估值财富也要与可变现现金分开。**

恢复选项在 Python Platform 会话的每个未结束事件边界中断，从检查点恢复，再把财务表与连续运行的结果比较。报告延迟时，策略可能还没看到已经发生的经济成交。会话保留这部分未结状态，防止重复提交。画面回放的是已经核对过的结果，没有现场杀死一个进程。

共享流动性选项把两个各买500股的请求合成一笔1,000股外部订单。一个行情区间只允许成交100股，分配器消费这一笔实际成交和费用。即使同一成交记录提供两遍，也只结算一次。本例采用确定的优先顺序，第一个子组合分到100股，第二个为零。每个子组合不会再获得一套独立的成交容量。

退出选项先买入500股，次日遇到交易锁定，随后容量只够卖出100股。最终现金6,000，仍持有400股。按最新价格10估值，财富为10,000，完全变现财富仍是未知。如果价格过期或缺失，估值财富也会变成未知。估值不能凭空增加卖出所得。

公司行为选项从200股和8,000元现金开始。除权日产生200元应收现金和200股应收权益，按4.5估值时财富仍为10,000。付款和解禁后，持仓成为400股，现金为8,200。另一个后续情境把每股估值改为3，入金前财富为9,400；存入1,000后，财富变为10,400。这笔存款是外部资金，不算交易利润。该后续情境的每个未结束事件边界也都经过恢复比较，包括权益和未送达报告。

风险审计按相同的一日区间和基点单位配对预测与结果。四个合成预测方差平均为2.5，实际残差平方平均为12.5，比值为5。缺失选项中，两条低流动性记录仍保留在报告里，该组覆盖率为零，方差诊断为未知。缺失结果没有被填成零损失，也没有从预测总数中消失。四个目标区间无法证明独立性或真实校准，原实现明确标记校准不可用、未获认证。

<!-- method:risk -->

??? details "进程恢复另有验收证据"
    这些画面验证 Platform 的财务状态恢复，包括延迟可见性。Runtime 负责进程监督和持久化任务恢复，其[财务会话文档](https://github.com/runchengxie/quant-backtest-runtime/blob/01ed4c34f955ef6cd39d13aa073b6d61b610d321/docs/financial-sessions.md)提供独立证据。浏览器回放没有复现那项进程中断验收。检查点哈希绑定输入与所加载代码，可以发现意外修改，不能抵御恶意作者篡改。

## 证据范围与复现入口

| 组件 | 本页检查了什么 | 证据仍未覆盖什么 |
| --- | --- | --- |
| Rust Engine | 合成报价成交、费用与最终余额 | Python 冲击模型、离散优化器和分钟策略不属于 Rust 能力 |
| Python Platform | 合成盘口撮合、冲击状态、费用与整股约束、独立账户、反馈、分配和财务恢复 | 真实市场校准、历史排队重建、实际清仓和未来盈利 |
| Runtime | 链接到已合并的公开进程恢复验收 | 动画本身没有启动或终止工作进程 |
| 教学选择搜索 | 固定无信号样例中的全部六个组合 | PBO/CSCV、一般误报控制和真实样本外证据 |

[样例 JSON](assets/method/fixtures.json)保留了已合并的精确组件版本、源代码与输入哈希，还有时钟、单位和经济输出。导出器文件哈希标识实际执行的代码，即使当时文件尚未提交也能核对。页面在构建时嵌入本地状态，不会向站点外请求数据、脚本、字体或遥测。

正常的 Rust、独立 Python 客户端和文档构建都不依赖 Platform 或 Runtime。重新导出样例时，需要按 JSON 中的固定公开版本准备干净检出，并使用单独锁定、包含微观结构依赖的 Platform 开发环境。Engine 从记录的源版本构建，再把明确路径传给导出器。环境、构建和输出目录放在源码仓库外。

```bash
python project_tools/export_method_fixtures.py \
  --platform "$PLATFORM_CHECKOUT" --runtime "$RUNTIME_CHECKOUT" \
  --engine "$ENGINE_BINARY" --output "$OUTPUT_DIR/fixtures.json"
python -m unittest discover -s project_tools -p 'test_method_*.py'
node --test project_tools/test_method_replay.cjs
```

设置 `METHOD_OWNER_PARITY=1`、`METHOD_PLATFORM`、`METHOD_RUNTIME`、`METHOD_PYTHON` 和 `QUANT_ENGINE_BINARY`，即可调用原实现重新导出，并与仓库样例逐字节比较。[开发与验证](development.zh-CN.md)说明锁定的文档构建和已有 Rust、客户端检查。[能力与兼容性](capabilities.zh-CN.md)列出 Engine 的准确支持范围。

挂载控件测试使用单独的工具目录。把 `project_tools/method-tests/package.json` 及其锁文件复制过去，运行 `npm ci --ignore-scripts`，再把 `NODE_PATH` 指向该目录的 `node_modules`，执行 `node --test project_tools/test_method_dom.cjs`。这类 DOM 单元测试检查行为，不等同于真实浏览器验收。手动触发的 **Method fixture owner parity** 工作流会在独立任务中调用固定公开版本重新生成样例，正常构建仍不依赖这些组件。
